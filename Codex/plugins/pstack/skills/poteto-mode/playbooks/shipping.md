# Shipping

Read ../../../references/codex-runtime.md.

Confirm the requested destination and existing authorization for publication, merge, or deployment. Preserve the user's gates. Resolve the active forge, actual trunk, and a frozen bottom-to-top list for any dependent PR stack. Independent changes stay outside that chain. The following gates concern Git state and evidence and apply with native Codex tools.

1. **Verify every PR independently.** Give a read-only verifier that did not author the change the PR's actual base/head and the real surface to exercise, including relevant positive and negative checks. Run verifiers concurrently when available and authorized, or as separate sequential reviewers when parallel capacity is unavailable. Each returns `PASS`, `PASS+NOTES`, `FAIL`, or `BLOCKED` with raw evidence. Record who verified it, the exact base/head SHAs, a stable `git patch-id` of the base-to-head diff, and checks/build artifacts. CI green and author self-proof do not replace this verdict. If no independent verifier is available, prepare the evidence, report that gate missing, and stop at merge-ready. Only an explicit user decision can change the gate. Publish a verdict to the PR only when that external comment is authorized; otherwise keep it in the local handoff.
2. **Freeze the verified ceiling.** Walk up from the lowest unmerged PR and stop at the first missing or nonpassing independent verdict. Both `PASS` and `PASS+NOTES` pass. A passing descendant above an unverified dependency is not landable. Extracting an independent descendant onto trunk requires fresh verification against that trunk base before it joins a landing run. Name the ceiling and the gap. Extending it requires another verification pass.
3. **Check freshness before every landing.** Compare the recorded patch-id with the current actual base-to-head patch-id after any rebase, retarget, or new commit. Changed patches require fresh verification. For changes limited to tests, docs, or lint configuration, reuse a lane only after comparing what it built twice at the verdict revision and once at the current revision. Each observed difference must be proven baseline noise or an embedded commit identifier; report its files and evidence. Rerun the affected checks and review at the current head even then. A dev server or any lane without comparable build outputs cannot establish that exception and must rerun. Matching commit messages and older green checks are not freshness evidence. If the patch-id is unchanged, keep the code verdict but refresh current-head CI and mergeability.
4. **Prepare only the current bottom PR.** Fetch current trunk, rebase that lowest verified branch when needed, publish it only within the existing authority, and retarget that PR alone to trunk. Reapply the freshness gate after the changed Git state. Leave descendants' base targets and merge controls alone until their turn.
5. **Land one PR at a time.** Merge only the current verified bottom PR, using the user's requested merge strategy or the repository convention. Arm merge-when-ready only when requested and only for that PR. Do not prepare the next one until the active forge reports the current one merged into the intended trunk base; a queue acknowledgement or merge into an old parent is not that result. A per-PR auto-merge request does not prove that the stack is ready or that a different forge's queue is armed.
6. **Recompute after every confirmed merge.** Fetch trunk, confirm the resulting merged revision, remove that PR from the frozen list, then inspect the new bottom's actual base, head, patch-id, CI, and mergeability. Check whether the host retargeted it; never assume that happened. Repeat the freshness and preparation gates for this one PR.
7. **Watch the current frontier without changing the queue around it.** Use bounded waits through the forge or available native monitoring tools. Keep pending checks, queued/armed merges, and confirmed failures distinct. A pending or blocked state while checks run is not by itself a failure. Diagnose a stalled or failed frontier before any mutation. Do not infer merged state from a generic READY label; confirm the forge's merged state and resulting revision.
8. **Stop at the frozen ceiling.** Report the landed run, each verdict and verifier, the heads checked, any merge controls armed and how they were confirmed, the next unverified PR, and what verifying it requires. Never silently extend the run because a descendant has green CI.

These gates authorize no external action beyond the user's request. Use the supported source-control tools instead of requiring Cursor cloud agents, cloud lifecycle arguments, the removed watcher scripts, or a proprietary loop command.

Finish with the actual result, checks run, gaps, and the next concrete step if work remains.
